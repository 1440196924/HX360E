## 0. 结论速览

**总体结论：技术可行，但不是"换个编译目标"就能完成的工作，属于中大型移植项目。**

核心判断如下：

1. **可行性成立的关键依据**：XenDroid 的 C++ 内核（约 39.8 万行、1025 个文件）中，真正依赖 Android API 的只有约 **6,400 行平台胶水代码**。其余（AArch64 JIT、Vulkan 渲染后端、内核/CPU/APU 模拟）是标准 POSIX C++，理论上可在鸿蒙上直接编译。更关键的是，本仓库里的 `XE_PLATFORM_ANDROID` 宏是**被注释掉的**（`platform.h:38`），上游那套 Android 支持层（`*_android.cc`，93 处条件编译）根本没进构建——这意味着不需要移植它们，反而减少了工作量。

2. **Vulkan 路径完全成立**：已在本机 DevEco SDK 中确认 `vulkan/vulkan_ohos.h` 存在，提供 `VK_OHOS_surface` 扩展与 `vkCreateSurfaceOHOS()`；`VK_OHOS_SURFACE_EXTENSION_NAME` 自 API 10 起可用，`SystemCapability.Graphic.Vulkan` 在 syscap 清单中。图形链路为：**XComponent → OHNativeWindow → VkSurfaceCreateInfoOHOS → VkSurfaceKHR**。

3. **JIT（动态代码生成）可行，但需实机验证机制**：Xbox 360 模拟器依赖 AArch64 JIT 把生成的机器码变成可执行页。公开信息存在矛盾（有说 HarmonyOS 5.0.0(12) 起禁止匿名可执行内存），但**决定性证据是：PPSSPP / melonDS / RetroArch 已有鸿蒙原生移植并开源，且 PPSSPP 鸿蒙版确实编译了 ARM64 JIT**（`core_sources.cmake` 含 `Arm64Jit.cpp`、`Arm64IRJit.cpp`、`JitBlockCache.cpp`），其 `compatibleSdkVersion` 正是 `5.0.0(12)`。缓解方案是实现"文件映射双视图 → 文件映射+`MAP_EXECUTABLE` → 匿名 RWX → mprotect 切换"四策略运行时探测（XenDroid 已内置第一种）。**仍需 Phase 0 真机实测**（见 §2.4、§5 Phase 0）。

4. **最大的工作量在前端**：Android 端有 79 个 Kotlin 文件、10,193 行 Compose UI，鸿蒙侧需要用 ArkTS/ArkUI 重写。这部分比 C++ 平台层重写的工作量更大。

5. **存储模型是最大的产品体验差异**：Android 用 `MANAGE_EXTERNAL_STORAGE` 全盘扫描游戏库，鸿蒙没有等价权限，只能通过文件选择器授权目录。这会导致"扫描整个 SD 卡找游戏"的体验无法照搬。

6. **编译器与 C++ 标准不是障碍（已实测）**：BiSheng 与 SDK 自带 clang 均为 **clang 15.0.4**，产物 ABI 完全等价（`build-profile.json5` 的 `nativeCompiler` 可切换）。C++20 逐特性实测：`std::filesystem`（813 处）、`std::span`（115 处）、concepts 等全部可用，**仅 6 个调用点**需改（`std::ranges` 算法 3 处、`std::jthread` 2 处、`std::atomic_ref` 1 处）。详见 §8。

**工作量粗估**（详见 §6）：

| 里程碑 | 预估 |
| --- | --- |
| Phase 0 关键技术验证（JIT + Vulkan + 音频 + GPU 能力 + 存储，共 5 项 demo） | 2–4 周 |
| 内核跑通（能进游戏、有画面、无前端） | 2–3 人月 |
| 可用 MVP（含基础 ArkTS 前端） | 6–9 人月 |
| 功能对等完整版 | 12–18 人月 |

## 1. 源项目剖析

### 1.1 架构分层

XenDroid 是双模块 Gradle 工程（`settings.gradle:22-24`）：

```
:app              纯 Kotlin/Compose 前端（79 个 .kt，10,193 行）
   ↓ 调用
:emulator-core    6 个 .java（1,251 行）JNI 绑定类 + CMake 原生构建
   ↓ JNI
libe.so           xendroid.cpp / emulator.cpp / emulator_xendroid.cpp
                  / xendroid_emu.cpp（40 个文件，约 7,400 行平台胶水）
   ↓ 链接
xenia 内核        src/xenia/**（1025 个文件，约 398,438 行）
                  + third_party/**（55 个依赖）
```

产物：`libe.so`（模拟器主体）与 `libhardware_ProcessorInfo.so`（Vulkan 物理设备探测），仅 `arm64-v8a`。

### 1.2 代码规模（关键子系统）

| 子系统 | 路径 | 行数 | 平台耦合度 |
| --- | --- | --- | --- |

| AArch64 JIT 后端 | `xenia/src/xenia/cpu/backend/a64/` | 14,909 | 仅可执行内存分配 |

### 1.3 一个重要的架构发现

`xenia/src/xenia/base/platform.h:26-46` 的平台分派中：

| --- | --- |

### 2.4 JIT / 可执行内存 ⚠️ 高风险，但已有成功先例

**结论：鸿蒙上 JIT 是可行的，已有第三方模拟器实证。** 但机制依赖系统版本与加固模式，必须实机验证。

#### 2.4.1 决定性证据：PPSSPP 鸿蒙原生移植

社区已有 **PPSSPP / melonDS / RetroArch 的鸿蒙原生移植并开源**（作者 richshaw2015）：

- https://github.com/richshaw2015/ppsspp
- https://github.com/richshaw2015/nds
- https://github.com/richshaw2015/retro

PPSSPP 的 PSP 模拟依赖**动态重编译器（JIT）**。检查其鸿蒙构建的源文件清单 `ohos/entry/src/main/cpp/core_sources.cmake`，确认 **ARM64 JIT 确实被编译进鸿蒙版本**：

```
Core/MIPS/ARM64/Arm64Jit.cpp
Core/MIPS/ARM64/Arm64IRJit.cpp
Core/MIPS/ARM64/Arm64Asm.cpp
Core/MIPS/ARM64/Arm64IRAsm.cpp
Core/MIPS/ARM64/Arm64RegCache.cpp
Core/MIPS/ARM64/Arm64IRRegCache.cpp
Core/MIPS/JitCommon/JitBlockCache.cpp
Core/Util/DisArm64.cpp
Common/Arm64Emitter.cpp
```

其 `ohos/build-profile.json5` 配置为 `compatibleSdkVersion: "5.0.0(12)"`、`targetSdkVersion: "6.0.0(20)"`、`runtimeOS: "HarmonyOS"` —— **正是 JIT 限制生效的版本区间**，且该移植已发布可用。这是"JIT 在鸿蒙上可行"的最强证据。

#### 2.4.2 可执行内存的分配机制（PPSSPP 的做法）

PPSSPP 的可执行内存分配在 `Common/MemoryUtil.cpp` 的 `AllocateExecutableMemory()`：

```cpp
int prot = PROT_READ | PROT_WRITE | PROT_EXEC;
if (PlatformIsWXExclusive()) prot = PROT_READ | PROT_WRITE;  // exec 稍后由 mprotect 加上
void* ptr = mmap(map_hint, size, prot, MAP_ANON | MAP_PRIVATE, -1, 0);
```

即**匿名 mmap 直接申请 RWX**（W^X 平台则退化为 mprotect 切换）。其 JIT 代码块通过 `CodeBlock.h` 的 `GetWritablePtrFromCodePtr()` 在"写指针"与"代码指针"之间换算，本质上也是双视图/双态方案。

值得注意的是，PPSSPP 在 `ppsspp_config.h` 中的平台分派与我们对 XenDroid 的建议完全一致：

```c
#elif defined(OHOS) || defined(__OHOS__)
// HarmonyOS / OpenHarmony
#define PPSSPP_PLATFORM_OHOS 1
#define PPSSPP_PLATFORM_LINUX 1
```

#### 2.4.3 相互矛盾的公开信息（必须实机验证的原因）

| 说法 | 来源 | 与 PPSSPP 的关系 |
| --- | --- | --- |
| 匿名内存 `PROT_EXEC` 自 5.0.0(12) 起被禁止 | 51CTO 问答、CSDN 适配文章 | 与 PPSSPP 的做法（匿名 RWX）**矛盾** |
| JIT 内存的 `mmap` 必须带 `MAP_EXECUTABLE`（内部等同 `MAP_JIT`），否则失败 | servo/mozjs 补丁（作者为华为工程师） | 适用于"先 PROT_NONE 再 mprotect"的分配模式 |
| 内核 XPM 在 `mmap_region` / `file_mprotect` 钩子拦截；匿名可执行由 SELinux `SECCLASS_JIT_MEMORY` 门控；`advsecmode.state=1` 时无条件拒绝 | OpenHarmony 内核文档 | 说明限制是**可配置的**，与设备加固模式有关 |

**合理解释**：限制强度取决于系统版本、设备加固模式（`advsecmode`）与应用签名/审核状态。PPSSPP 能跑通说明在常规设备与常规签名下 JIT 可用，但不同分配模式（直接 RWX / 先 RW 再 mprotect / 文件映射）的通过率不同。

#### 2.4.4 XenDroid 的现状与移植策略

XenDroid 的代码缓存（`cpu/backend/code_cache_base.h:174-319`）**已经内置了 W^X 安全的文件映射双视图方案**——同一 memfd 对象分别映射为 RX 视图与 RW 视图，没有任一映射同时具备 W 和 X：

```cpp
generated_code_execute_base_ = MapFileView(mapping_, exec_addr, size, kExecuteReadOnly, 0);
generated_code_write_base_   = MapFileView(mapping_, write_addr, size, kReadWrite, 0);
```

这是最保守、最可能通过鸿蒙安全策略的路径。当前问题是 `base/memory.cc:20` 的 `writable_executable_memory` cvar **默认 true**，会让它走匿名 RWX 快路径。

**建议实现"多策略 + 运行时探测"**，按优先级依次尝试：

| 优先级 | 策略 | 说明 |
| --- | --- | --- |
| 1 | 文件映射双视图（RX + RW） | XenDroid 已有，最保守。`memfd_create` + 两次 `mmap` |
| 2 | 文件映射 + `MAP_EXECUTABLE` | mozjs 方案，应对"必须带标志"的系统版本 |
| 3 | 匿名 RWX | PPSSPP 方案，`MAP_ANON\|MAP_PRIVATE` + `PROT_READ\|WRITE\|EXEC` |
| 4 | 匿名 RW + `mprotect` 切换 | 最后的兜底，运行时按页切换 |

启动时依次探测（写一段 `mov x0,#42; ret` 并调用），记录可用策略到日志。

**其他必要改动**：

1. `base/memory_posix.cc:368-375`：`ASharedMemory_create()`（Android ashmem）换成 `memfd_create()`。注意 PPSSPP 的 `MemArenaOhos.cpp` 已经验证了 `memfd_create` 在鸿蒙上可用（其 syscall 号 ARM64 = 279）。
2. `emulator-core/src/main/cpp/xe_a64_code_cache_posix.cpp:15,948`：`extern "C" void __clear_cache(...)` 是 **bionic 专有符号**，鸿蒙不存在，改为 `__builtin___clear_cache()`。
3. `base/memory_posix.cc:121-148`：`IsWritableExecutableMemorySupported()` 在 OHOS 上不要无条件返回 `true`，改为返回探测结果。

**必须验证**：在目标设备（真机）上跑通上述 4 种策略中的至少一种。这是 Phase 0 的第一优先事项。

> ⚠️ **许可证提醒**：PPSSPP / melonDS / RetroArch 的鸿蒙移植是 **GPL-2.0** 许可，而 XenDroid 核心是 **BSD**（`memory_posix.cc` 等 995 个文件头部均为 BSD，xenia 源码树中无 GPL 文件）。**不要直接复制它们的代码**，只能参考思路后自行实现，否则会污染 XenDroid 的许可证。

### 2.5 音频 ✅ 支持，需新写驱动

这些与 AAudio 的 API 形状高度相似，**按 `xe_aaudio_audio_driver.cpp` 的结构照搬即可**，预估 400–600 行新代码。

### 2.6 输入 ✅ 支持

### 2.7 存储 ⚠️ 最大的产品差异

| 方面 | Android | HarmonyOS |
| --- | --- | --- |
| 全盘访问 | `MANAGE_EXTERNAL_STORAGE` | **无等价权限** |
| 目录访问 | 任意路径 `java.io.File` 遍历 | picker 选择文件/目录（可配合 `@ohos.fileshare.persistPermission` 持久化授权，需 `FILE_ACCESS_PERSIST`） |
| URI 体系 | `content://` + `ContentResolver` + `DocumentsProvider`（519 行） | 无 `DocumentsProvider` 等价物 |

**产品模型的调整：从"扫描"改为"安装"**

鸿蒙应用运行在沙箱中，无法像 Android 那样扫描全盘。**本项目的设计选择是把游戏文件安装（拷贝）到沙箱**，之后所有访问都是沙箱内的真实 POSIX 路径。详细设计见 [DESIGN.md §10](./DESIGN.md)。

| 影响面 | 说明 |
| --- | --- |
| 游戏库来源 | `data/GameLibraryRepository.kt`（243 行）的"扫描全盘"逻辑废弃，改为"扫描沙箱 `games/` 下的 `install.json`" |
| 自建文件浏览器 | `ui/library/FolderBrowserScreen.kt`（237 行）不再需要（无目录扫描场景） |
| 新增安装器 | picker → 预检（格式/元数据/空间）→ 流式拷贝（带进度）→ 校验 → 原子落定 |
| `DocumentsProvider` | 519 行，无对应机制，**删除**；改为应用内的存档导出/导入界面（沙箱化的副作用：用户看不到存档） |
| 空间成本 | 游戏文件占用 **2×**（源文件 + 沙箱副本）；上游的 `compressIsoToZar` 因此价值更高 |
| 换盘 | 多光盘游戏各盘独立安装，共享 titleId 的配置与存档 |
| native 侧 | **零改动**——拿到的是沙箱内真实路径，内核 VFS 层照常工作；上游的 fd 变体（`BOOT_TYPE_WITH_FD`）可不启用 |

### 2.8 进程模型 ⚠️ 需要调整

Android 版采用双进程（`AndroidManifest.xml:56` 的 `:emu`），目的是**硬杀进程**来彻底清理模拟器状态（`EmulatorHostActivity.kt:527` 调用 `Process.killProcess`）。

鸿蒙没有应用自有的多进程模型（`AbilityKit/native_child_process.h` 提供 `OH_Ability_CreateNativeChildProcess`，但受限且需要审核）。

**建议**：改为单进程 + 优雅退出。模拟器本身有 `quit()` / `is_running()` 接口（`emulator.cpp:483-485`），但注意当前 `ae::quit` 是空桩（`xendroid_emu.cpp:855-856`），需要补实现。

## 4. 风险清单

| 编号 | 风险 | 等级 | 说明与缓解 |
| --- | --- | --- | --- |
| **R1** | **JIT 可执行内存被拦截** | 🟡 中（有成功先例，仍需实测） | 匿名 `PROT_EXEC` 的策略随系统版本/加固模式变化。**PPSSPP 鸿蒙版已编译并运行 ARM64 JIT**（`compatibleSdkVersion 5.0.0(12)`），证明可行（见 §2.4.1）。缓解：实现"文件映射双视图 → 文件映射+`MAP_EXECUTABLE` → 匿名 RWX → mprotect 切换"四策略运行时探测（见 §2.4.4）。**Phase 0 必须实机验证** |
| **R2** | **GPU 性能不足** | 🔴 高 | XenDroid 官方要求 Snapdragon Gen2+ / Adreno 740+。华为设备为自研 Maleoon GPU，驱动成熟度未知。Kirin 9020（Maleoon 920）支持 Vulkan 1.3.275，但**能否跑动 Xbox 360 游戏完全是未知数**。需实机 benchmark |
| **R3** | **无法使用自定义 Vulkan 驱动** | 🟡 中 | Android 上用户可加载 Turnip 驱动绕过厂商驱动缺陷（README 明确推荐）。鸿蒙无 libadrenotools 等价机制，只能吃系统驱动，遇到驱动 bug 无解 |
| **R4** | **存储/文件访问模型差异** | 🟡 中 | 无法全盘扫描游戏库。**已定方案：游戏"安装"到沙箱**（拷贝 → 之后只用沙箱内真实路径），代价是空间 2× 与首次安装耗时。存档也在沙箱内，需提供导出/导入。详见 §2.7 与 [DESIGN.md §10](./DESIGN.md) |
| **R5** | **C++20 标准库/编译器能力** | 🟢 低（已实测） | clang 15 + libc++ 15。逐特性实测（见 §8.5）：`std::filesystem`（813 处）、`std::span`（115 处）、concepts、`[[likely]]` 等全部可用；仅 **6 个调用点**因 libc++ 15 缺失而需改：`std::ranges::equal/find_if/distance`（3 处）、`std::jthread`（2 处）、`std::atomic_ref`（1 处）。改动量约 6 行 |
| **R6** | **seccomp / 沙箱限制** | 🟡 中 | `clone3` 不在白名单（需改用 `clone`）；带 namespace flag 的 `clone` 会被 TRAP；`/proc/self/maps`、`/proc/cpuinfo` 可见性未验证。缓解：实测 + 用替代实现 |
| **R7** | **x86_64 模拟器无法运行** | 🟡 中 | AArch64 JIT 无法在 x86_64 上工作。DevEco 模拟器将无法测试，必须真机 |
| **R8** | **上架合规审核** | 🟡 中 | 模拟器类应用涉及 JIT、子进程、大内存，华为应用市场需提交必要性说明。建议提前沟通 |
| **R9** | **libunwind 兼容性** | 🟢 低 | `xe_a64_code_cache_posix.cpp` 用 `__register_frame` / `_Unwind_Backtrace` 实现 128 MiB DWARF `.eh_frame` 表。OHOS 有 libunwind，但注册路径需验证 |
| **R10** | **实时线程优先级** | 🟢 低 | `threading_posix.cc` 使用 `SCHED_FIFO` + `pthread_setschedparam`。OHOS 头文件齐全，但普通应用可能无权限设置实时优先级，会静默降级 |

## 7. 建议

1. **先做 Phase 0，尤其是 JIT 验证**。这是唯一的"一票否决"项。在它通过之前不要投入任何大规模开发。
2. **架构上采取"核心复用 + 平台层重写"**，不要试图把 Android 平台层改造成跨平台层——`XE_PLATFORM_ANDROID` 本来就是死代码，直接为 OHOS 写一套干净的新平台层更省事。
3. **图形后端按需求只做 Vulkan**，这一点与源项目天然契合：D3D12/Metal 后端在 Android 构建中本来就被排除，Vulkan 是唯一被编译的图形后端。
4. **前端不要追求功能对等起步**。Android 版 10,193 行 Compose UI 中，很多是游戏库扫描、内容管理、配置文件编辑器等"锦上添花"功能。MVP 只需：能选游戏、能进游戏、能操作、能退出。
5. **对 R2（GPU 性能）保持清醒**。即使一切编译通过，Xbox 360 模拟对 GPU 的压力远超普通游戏。建议 Phase 0 同时用 `Xenia Edge` 桌面版在一台性能相近的设备上跑一个简单游戏，作为性能天花板参考。
6. **保留回退能力**：Phase 0–2 期间保持代码与上游 XenDroid 的同步（用 `patches/` 目录管理差异），避免分支漂移后无法吸收上游修复。
7. **上游同步按 §9 的方案执行**：fork + `harmony` 分支做开发，导出补丁到 `patches/harmony/` 存档，submodule 锁定 commit 保证构建可复现。补丁尽量"新增文件优先、条件编译优先、单一职责"，控制在 15–25 个以内。
8. **注意许可证边界**：XenDroid 是 BSD，PPSSPP/melonDS/RetroArch 的鸿蒙移植是 GPL-2.0——**参考思路可以，复制代码会污染许可证**。

## 8. 编译器与 C++ 标准实测（补充分析）

本节回答一个具体问题：**不用 BiSheng，用官方 clang 能否编译出鸿蒙可加载的静态库/动态库？C++20 标准能否满足？**

### 8.1 结论

**能，而且换编译器解决不了 C++ 标准问题。** 两个工具链都是 **clang 15.0.4 + libc++ 15.0.4**，C++20 支持能力完全相同。真正需要处理的是 **6 处 libc++ 15 缺失的标准库特性调用点**，改动量极小。

### 8.2 两个工具链的关系

| | BiSheng | Original（官方） |
| --- | --- | --- |
| 编译器 | `hms/native/BiSheng/bin/clang` 15.0.4 | `openharmony/native/llvm/bin/clang` 15.0.4 |
| toolchain 文件 | `hmos.toolchain.bisheng.cmake` | `hmos.toolchain.cmake`（内部 include `ohos.toolchain.cmake`） |
| libc++ 头文件 | `BiSheng/include/libcxx-ohos/...` | `llvm/include/libcxx-ohos/...` |
| ABI 命名空间 | `std::__n1` | `std::__n1` |
| sysroot | `openharmony/native/sysroot` | 同左 |

**切换方式**：项目根 `build-profile.json5:12` 的 `"nativeCompiler"` 字段，schema 允许值为 `"Original"`（默认）与 `"BiSheng"`。hvigor 的选路逻辑（`build-native-with-cmake.js` → `getToolchainFile`）为：

```
nativeCompiler === "BiSheng" 且 runtimeOS === "HarmonyOS"  → hmos.toolchain.bisheng.cmake
否则（Original）             且 runtimeOS === "HarmonyOS"  → hmos.toolchain.cmake
非 HarmonyOS（OpenHarmony）                                → ohos.toolchain.cmake
```

注意：`nativeCompiler: "BiSheng"` 只在 `runtimeOS: "HarmonyOS"` 下有效；当前项目正是这个组合。

### 8.3 产物等价性实测

同一份源码（libc++ 容器 + `std::filesystem` + NAPI 入口），分别用两个编译器编译：

```
官方 clang:  clang++ --target=aarch64-linux-ohos --sysroot=<OHOS sysroot> -D__MUSL__ -std=c++20 -shared
BiSheng:     同上
```

产物对比结果**完全一致**：

| 检查项 | 官方 clang | BiSheng |
| --- | --- | --- |
| ELF Class / Type | ELF64 / DYN | ELF64 / DYN |
| Machine | AArch64 | AArch64 |
| NEEDED | `libc++_shared.so`, `libc.so` | 同左 |
| 导出符号 | 完全相同 | 完全相同 |
| libc++ ABI | `std::__n1` | `std::__n1` |

另外实测通过官方 `ohos.toolchain.cmake` 走完整 CMake 流程，成功构建出正确解析 `libace_napi.z.so` / `libnative_window.so` / `libvulkan.so` 的 .so：

```
NEEDED  libace_napi.z.so
NEEDED  libnative_window.so
NEEDED  libvulkan.so
NEEDED  libc++_shared.so
NEEDED  libc.so
SONAME  libxetest.so
```

**结论：编译器不是约束条件。** 决定能否加载的是目标三元组（`aarch64-linux-ohos`）、sysroot、以及 libc++ ABI 一致性。

### 8.4 鸿蒙的双 C++ 运行时模型（关键约束）

鸿蒙把 C++ 标准库拆成两套，**不能混用**：

| 类型 | 库 | 发布方式 | 内联命名空间 |
| --- | --- | --- | --- |
| 系统库 | `libc++.so` | 随系统镜像 | `std::__h` |
| 应用 Native 库 | `libc++_shared.so` | **随应用打包** | `std::__n1` |

本机实测印证：SDK 的 `libc++_shared.so` 导出符号确实是 `_ZNSt4__n1...`，而 `llvm/include/c++/v1/__config_site` 里另一套配置写的是 `__1`（那是给主机工具用的），**编译器实际使用的是 `libcxx-ohos` 那一套，命名空间为 `__n1`**。

**对移植的三点影响**：

1. **必须用 SDK 的 `libcxx-ohos` 头文件**，否则符号前缀不匹配，链接或运行时失败。
2. **`libc++_shared.so` 必须打包进 HAP**（放在 `entry/libs/arm64-v8a/`），系统不提供应用用的这一份。或改用静态链接规避（见下）。
3. **Native API 全部是 C 接口**（NAPI、Vulkan、OHNativeWindow、OHAudio、GameControllerKit 都是 C API），所以 C++ ABI 不会跨越到系统侧。这意味着我们在自己的 .so 内部对 C++ 运行时的选择是自由的——这是移植的一个有利条件。

**静态 vs 动态链接 C++ 运行时的选择**：

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| 动态（默认） | `OHOS_STL=c++_shared`，打包 `libc++_shared.so` | 多个 .so 互相传递 C++ 对象时**必须**用这个，否则 ODR 违规 |
| 静态 | `OHOS_STL=c++_static` 或 `-static-libstdc++` | 只有一个 .so 时推荐，无需打包，产物更小 |

实测 `-static-libstdc++` 有效：产出的 .so 的 NEEDED 只剩 `libc.so`（体积从 22 KB 增至 2.98 MB，因为内含 libc++）。

**XenDroid 的场景**：`libe.so` 是一个大的自包含 .so，只在 NAPI 边界与系统交互，所以**静态链接 libc++ 是可行的**，能省掉打包 `libc++_shared.so` 的麻烦。但如果后续拆出多个 .so（例如把 `libhardware_ProcessorInfo.so` 也保留），则必须统一用动态链接。

### 8.5 C++20 特性逐项实测

用 BiSheng（clang 15.0.4）以 `-std=c++20` 逐特性编译测试：

**✅ 可用**（XenDroid 实际用到的）：

| 特性 | 内核使用量 |
| --- | --- |
| `std::span` | 115 处 |
| `std::string_view::starts_with` / `ends_with` | 31 / 11 处 |
| `std::endian`、`std::bit_cast`、`std::bit_ceil`、`std::countl_zero` | 23 / 3 处 |
| `std::filesystem`（含 `directory_iterator`） | **813 处** ← 最重要的通过项 |
| concepts / `requires` 约束 | `base/chrono.h:80,100`、`kernel/xconfig.h:398`、`kernel/xobject.h:499`、`kernel/util/shim_utils.h:484,490` |
| `[[likely]]` / `[[unlikely]]` | 6 处 |
| `std::midpoint`、`std::ssize`、`std::to_address`、`std::numbers` | — |
| `std::latch` / `std::barrier` / `std::counting_semaphore` / `atomic::wait` | 头文件存在且可用 |
| `constexpr` 动态分配（`constexpr std::vector`） | — |
| 指定初始化器、三路比较、模板 lambda | — |

**❌ 不可用**（需要改代码）：

| 特性 | 内核调用点 | 修复方式 | 工作量 |
| --- | --- | --- | --- |
| `std::ranges::equal` | `base/string_key.h:78` | 改 `std::equal` | 1 行 |
| `std::ranges::find_if` | `kernel/xam/xdbf/spa_info.cc:510` | 改 `std::find_if` | 1 行 |
| `std::ranges::distance` | `ui/imgui_drawer.cc:739` | 改 `std::distance` | 1 行 |
| `std::jthread` | `kernel/xam/xam_ui.cc:90,157` | 改 `std::thread` + 手动 `detach()`（代码里本来就调了 `t.detach()`） | 2 处 |
| `std::atomic_ref` | `cpu/xex_module.h:52` | 改 `__atomic_load_n` / `__atomic_store_n` 内建 | 1 处 |
| `std::source_location` | 无使用（D3D12 里只有同名局部变量） | — | 0 |

**合计需要修改 6 个调用点**（`std::ranges` 3 处 + `std::jthread` 2 处 + `std::atomic_ref` 1 处）。其中 `kernel/xam/xam_ui.cc` 确实在构建中（`kernel/CMakeLists.txt:2` 的 `xe_platform_sources(... RECURSIVE)`），所以必须改。

其他 C++20/23 特性（`std::format`、`std::osyncstream`、`std::mdspan`、`std::expected`、`std::print`、`std::stacktrace`、`std::byteswap`、`std::to_underlying`、`std::atomic<std::shared_ptr>`）在内核中**均无使用**，不构成障碍。

### 8.6 如果一定要用更新的 clang（如 LLVM 18/19/20）

理论上可行，但**收益很小、风险不小**：

- 目标三元组、sysroot、`-D__MUSL__` 都可以照搬。
- **但必须继续使用 SDK 的 `libcxx-ohos` 头文件与 `libc++_shared.so`**（保持 `std::__n1`），否则 ABI 不匹配。而 `std::ranges` 算法、`std::jthread`、`std::atomic_ref` 是**头文件层面**的特性，libc++ 15 的头里没有，换编译器也变不出来。
- 想同时拿到新版 libc++，就得把新版 libc++ 静态链进自己的 .so。此时要处理与进程内其他 `libc++_shared.so` 的符号互串问题（两者都用内联命名空间，`std::__n1` vs `std::__1` 若撞名会很难查），收益与风险不成比例。
- 另一个现实约束：**一个应用包内的多个 .so 必须用同一大版本 clang 工具链编译**，并依赖相同版本的 libc++_shared，否则可能出现 `symbol not found` 之类的错误。引入第三个编译器版本会破坏这个前提。

**建议：就用 SDK 自带的 clang（Original 或 BiSheng），修掉那 6 个调用点。** 不需要为了 C++ 标准去换编译器。

### 8.7 构建配置的配套修改

| 项 | 现状 | 应改为 |
| --- | --- | --- |
| `nativeCompiler` | `"BiSheng"`（`build-profile.json5:12`） | 保持 `BiSheng` 或改 `"Original"`，二者产物等价 |
| `cppFlags` | `--std=c++14`（`entry/build-profile.json5:12`） | `--std=c++20` |
| `CMAKE_CXX_STANDARD` | 未设置（顶层 CMakeLists） | 在 HX360E 顶层 `entry/src/main/cpp/CMakeLists.txt` 加 `set(CMAKE_CXX_STANDARD 20)` + `set(CMAKE_CXX_STANDARD_REQUIRED ON)`，覆盖 NAPI 桥与 xendroid 子树 |
| `abiFilters` | `["arm64-v8a", "x86_64"]` | 只留 `arm64-v8a`（AArch64 JIT 无法在 x86_64 上工作） |
| C++ 运行时 | 未指定 | 单 .so 场景建议 `-static-libstdc++`；多 .so 场景打包 `libc++_shared.so` |
| `cmake_minimum_required` | `3.5.0`（`entry/src/main/cpp/CMakeLists.txt:2`） | `3.20+`（内核要求，SDK 自带 CMake 3.28.2） |

**官方文档给出的两种改法与它们的关系**（华为 FAQ《如何修改代码工程所支持的C++语言版本》，2026-06-26 更新）：

官方提供两种方式：① CMakeLists 里 `set(CMAKE_CXX_STANDARD 20)`；② `build-profile.json5` 里 `"cppFlags": "--std=c++20"`。

两者**同时设置时谁生效**？本机实测（同一份用到 `std::span`/`std::endian` 的 C++20 源码，OHOS 工具链）：

| 场景 | 实际编译命令中的 `-std` | 结果 |
| --- | --- | --- |
| 只有 `cppFlags=--std=c++14`（= 项目现状） | `-std=c++14` | ❌ C++20 代码编译失败 |
| `cppFlags=--std=c++14` + `CMAKE_CXX_STANDARD=20` | `-std=c++14 -std=gnu++20` | ✅ 成功（**后者覆盖前者**） |
| 只有 `cppFlags=--std=c++20` | `-std=c++20` | ✅ 成功 |

**结论**：`cppFlags` 进入 `CMAKE_CXX_FLAGS` 排在命令行前面，`CMAKE_CXX_STANDARD` 追加的 `-std=gnu++20` 排在后面，因此**后者生效**。但依赖 flag 顺序是脆弱的（将来 CMake 改变参数顺序就会失效），**建议两处都设成 c++20**，保持一致。

另外两点官方文档未覆盖、但对本项目重要：

- 官方文档示例用 `CMAKE_CXX_STANDARD 17`，**本项目需要 20**，别照抄。
- 官方文档只说明"C++17 和 C++20 正在逐步完善"，没有给出缺口清单。**§8.5 的逐特性实测矩阵就是这份缺口的精确答案**（6 个调用点）。
- 官方文档未提及 `nativeCompiler`（BiSheng / Original 切换）。该选项**不影响 C++ 标准能力**（两者都是 clang 15.0.4 + libc++ 15.0.4），只影响编译器后端。

## 9. 上游同步与补丁管理方案

需求：**XenDroid 作为上游，我们做修改但不回提上游，改动以补丁形式存在于我们自己的项目里。**

### 9.1 三种可选方案

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. fork + harmony 分支** | fork `rfandango/XenDroid` 到自己的仓库，建 `harmony` 分支放全部改动；上游更新时 `git rebase upstream/main harmony` | 冲突解决方便，git 工具链完整；改动是一等公民的 commit | 需要一个 fork 仓库（可私有） |
| **B. submodule 指向上游 + `patches/` 目录** | submodule 直接指向上游，改动以 `.patch` 文件形式存在，构建前 `git apply` | 补丁显式可见、可审计；submodule 干净跟随上游 | 上游更新后补丁易失效；改动多时 `git apply` 冲突难处理 |
| **C. vendored 源码快照** | 把 XenDroid 源码复制进项目 | 完全自控 | **不可取**：39.8 万行代码进主仓库，仓库体积与历史爆炸 |

### 9.2 推荐：A + B 混合

**日常开发用 A（fork + `harmony` 分支），同时导出补丁到 `patches/` 用作文档与审计。**

```
HX360E/                                  # 鸿蒙应用仓库（我们的项目）
├── entry/src/main/cpp/
│   ├── CMakeLists.txt                   # 顶层：add_subdirectory(xendroid) + NAPI 桥
│   ├── napi_init.cpp                    # NAPI 桥（对应原 JNI 层）
│   └── xendroid/                        # git submodule → 我们的 XenDroid fork，锁定 commit
├── patches/harmony/                     # 补丁序列（由 git format-patch 导出）
│   ├── 0001-platform-ohos-macro.patch
│   ├── 0002-cmake-ohos-target.patch
│   ├── 0003-jit-memory-multi-strategy.patch
│   ├── 0004-cxx20-libcxx15-compat.patch
│   ├── 0005-ohos-surface-window.patch
│   ├── 0006-ohos-audio-driver.patch
│   └── 0007-disable-adrenotools-aaudio-opensles.patch
└── docs/
```

**工作流**：

```bash
# 一次性：克隆上游并建立 harmony 分支
git clone https://github.com/rfandango/XenDroid.git
cd XenDroid
git remote rename origin upstream
git checkout -b harmony

# 日常：在 harmony 分支上按"单一职责"提交
git commit -m "platform: add XE_PLATFORM_OHOS branch"
git commit -m "jit: multi-strategy executable memory allocation"

# 上游更新：rebase 到新的上游 main
git fetch upstream
git rebase upstream/main harmony

# 导出补丁（供 HX360E 仓库存档/审计）
git format-patch upstream/main..harmony -o ../HX360E/patches/harmony/
```

HX360E 侧用 submodule 锁定到 fork 的具体 commit，保证构建可复现：

```bash
git -C entry/src/main/cpp/xendroid submodule update --init --recursive
```

### 9.3 子模块的现实问题

`git submodule status` 显示 XenDroid 的 **55 个子模块目前全部未检出**（条目均以 `-` 开头）。完整初始化会拉取 FFmpeg、wxWidgets、DirectXShaderCompiler、MoltenVK、SDL3 等大量代码，其中大部分鸿蒙构建**根本用不到**。

**建议**：在 fork 里维护一份"鸿蒙必需子模块清单"，只初始化需要的：

**必需**：`fmt`、`Vulkan-Headers`、`VulkanMemoryAllocator`、`SPIRV-Headers`、`SPIRV-Tools`、`SPIRV-Cross`、`glslang`、`xbyak_aarch64`、`capstone`、`boost_context`、`imgui`、`pugixml`、`rapidjson`、`tomlplusplus`、`cxxopts`、`utfcpp`、`cereal`、`half`、`stb`、`xxhash`、`snappy`、`zlib-ng`、`zstd`、`zarchive`、`mspack`、`aes_128`、`dxbc`、`FidelityFX-CAS`、`FidelityFX-FSR`、`microprofile`、`disruptorplus`、`date`、`llvm`、`asio`、`libusb`、`FFmpeg`、`patches/xenia-canary`

**不需要**：`wxWidgets`、`MoltenVK`、`DirectXShaderCompiler`、`DirectX-Headers`、`SDL3`、`xbyak`、`metal-cpp`、`catch`、`cpplint`、`clang-format`、`binutils`、`discord-rpc`、`renderdoc`、`miniaudio`

### 9.4 补丁管理原则（降低 rebase 冲突）

1. **新增文件优先于修改文件**。例如新增 `surface_ohos.cc` / `window_ohos.cc`，而不是大改 `surface_android.cc`。
2. **平台分支集中**。所有 `XE_PLATFORM_OHOS` 判断尽量收敛在 `platform.h`、CMake、`memory_posix.cc` 这几个文件里。
3. **用条件编译而不是删代码**。不要物理删除 Android/AAudio/OpenSLES/adrenotools 的源文件，而是在 CMake 层面排除它们——这样上游改动不会撞上我们的删除。
4. **每个补丁单一职责**，一个补丁只做一件事，便于上游变更后单独 rebase 或丢弃。
5. **补丁数量控制在 15–25 个**。按 §3 的工作分解，改动集中在约 30–60 个文件，这个规模用补丁序列管理是合适的；如果补丁数失控，说明侵入性过强，应重新审视分层。
6. **定期同步**（建议每月），避免上游漂移过大导致 rebase 地狱。

### 9.5 许可证约束

| 项目 | 许可证 | 影响 |
| --- | --- | --- |
| XenDroid / Xenia 核心 | **BSD**（`memory_posix.cc` 等 995 个文件头部均为 BSD；xenia 源码树中无 GPL 文件） | fork、修改、闭源分发均可，保留版权声明即可 |
| PPSSPP / melonDS / RetroArch 鸿蒙移植 | **GPL-2.0** | **不可将代码复制进 XenDroid**，只能参考思路后自行实现 |

这一点在移植 JIT 内存分配（§2.4）和图形表面处理时尤其要注意——参考 PPSSPP 的**做法**是安全的，复制它的**代码**会污染 XenDroid 的 BSD 许可证。

## 10. 游戏兼容性对比分析（鸿蒙 vs Android）

问题：移植完成后，游戏兼容性会比 Android 版下降吗？

**结论：CPU 侧完全一致；GPU 侧会下降，但下降来自硬件/驱动，不是来自移植本身。**

### 10.1 不会变的部分

| 层面 | 原因 |
| --- | --- |
| **CPU 模拟 / JIT** | 同一份 `xbyak_aarch64` JIT 代码、同一份内核/内存/VFS 代码。只要可执行内存能分配成功（§2.4），CPU 模拟的兼容性**逐指令一致** |
| **Guest 补丁系统** | 形如 `patches/4D5307F1.patch.toml` 的 guest 内存补丁与宿主平台无关，照常生效 |
| **Vulkan 后端代码** | 同一份 33,899 行代码。**实测确认无硬编码厂商分支**（在 `gpu/vulkan` + `ui/vulkan` 中 grep `VK_VENDOR_ID` / `vendorID ==`，0 处命中） |
| **特性降级机制** | 扩展是能力探测式的，缺失即降级。可选扩展包括 `KHR_dynamic_rendering`（1.3 核心，1.2 走扩展）、`EXT_fragment_shader_interlock`、`EXT_custom_border_color`、`EXT_fragment_shader_barycentric`、`EXT_subgroup_size_control`、`EXT_extended_dynamic_state1/2/3`、`EXT_external_memory_host`、`KHR_fragment_shader_barycentric` 等；`sparseBinding`/`sparseResidencyBuffer` 也有降级路径 |

### 10.2 会变的部分：GPU 驱动（兼容性下降的真正来源）

XenDroid 的 GPU 调优**几乎全部是在 Adreno + Turnip 上测出来的**。`GAME_COMPAT.md` 里每个 workaround 都带 Adreno 标注：

| 配置项 | 针对的 Adreno 问题 | Maleoon 上是否需要重新调 |
| --- | --- | --- |
| `depth_float24_convert_in_pixel_shader` | Adreno/kgsl 的 float24↔float32 深度传输会触发 GPU fault → device-loss | 未知，需实测 |
| `vulkan_dynamic_constant_buffers` | 高通私有驱动（a650/a740/a830）下像素着色器读到全零 | 未知 |
| `vulkan_mid_frame_submission_draws` | kgsl Adreno 的重帧 GPU 空闲气泡（Forza 20→30fps） | 未知 |
| `vulkan_shared_memory_host_visible` | 统一内存 GPU 的 resolve 回读带宽优化（Adreno 830 上 +11.6% fps） | Maleoon 也是统一内存，可能适用 |
| `vulkan_hoist_shmem_uploads` / `vulkan_render_target_cache` 的 GMEM 相关项 | tile-based GPU 的 GMEM store/restore 开销 | Maleoon 也是 tile-based，可能适用 |
| Fable II 地面几何消失（未解决） | 精确逐片元深度测试 + reversed-Z + float24 精度问题，**在 Adreno 上都没解决** | 大概率同样存在，甚至更严重 |

`ui/vulkan/vulkan_instance.cc:56-58` 的 `AdrenoGeneration()` 会读 `/sys/class/kgsl/kgsl-3d0/gpu_model`——在鸿蒙上必然读不到（返回 0），但它只用于 Turnip 的 `TU_DEBUG` workaround，不影响其他逻辑。

**结构性损失：Android 上可以用 libadrenotools 换 Turnip 驱动来绕过厂商驱动 bug（README 明确推荐），鸿蒙没有等价机制。** 这意味着遇到 Maleoon 驱动缺陷时没有逃生通道。

### 10.3 两个必须分开看的问题

用户问的是"兼容性"（游戏能不能正常跑），但实际有两个独立风险：

| | 兼容性（正确性） | 性能（帧率） |
| --- | --- | --- |
| 决定因素 | 驱动正确性 + 模拟器 workaround 覆盖度 | GPU 绝对算力 + 驱动效率 |
| 鸿蒙侧现状 | 未知，需实测 | 未知，需实测 |
| 参考基线 | XenDroid 官方要求 Adreno 740+ | 同上 |

**注意**：XenDroid 官方设备要求是 "Snapdragon SoC GEN 2 or higher / Adreno GPU 740 or higher"。Maleoon 920 的纸面规格接近这一档，但**能否达到该性能基线本身是未知数**。即使兼容性 100%，性能不足同样导致游戏不可玩。

### 10.4 兼容性风险的时间尺度

模拟器在新 GPU 驱动上的兼容性，通常需要 **6–12 个月**的"驱动修复 + 模拟器侧 workaround 积累"才能接近成熟平台的水平。这个过程在 Android 上已经走了很久（`GAME_COMPAT.md` 里的记录从 2026-06 开始，`docs/` 里的 GPU 调研针对 Adreno 650/830）。

鸿蒙侧意味着**重新开始积累**。

### 10.5 缓解措施

1. **建立设备/驱动 profile 系统**。参考 PPSSPP 的做法，按 GPU 型号预设 cvar 组合。好消息是上述调优**全部是 cvar**，不需要改代码就能按设备调整——这是现有架构给的缓冲。
2. **保留 Android 版作为 A/B 对照基准**。项目 README 本来就要求"与 Xenia Edge 的 Vulkan 后端对比"，移植后应继续用它来区分"移植引入的 bug"和"上游本来就有的 bug"。
3. **Phase 0 的 0.4 项扩展为"能力探测 + 已知游戏矩阵"**：不只看特性清单，还要实际跑几个已收录在 `GAME_COMPAT.md` 里的标题（Ninja Gaiden 2、Fable II），记录表现。
4. **优先在 Kirin 9020（Maleoon 920 / Vulkan 1.3.275）验证**，把 Kirin 9010（Maleoon 910 / Vulkan 1.2.275）作为兼容性下限——后者缺 1.3 核心特性，要走 `VK_KHR_dynamic_rendering` 扩展路径。
5. **对"某些标题在鸿蒙上就是跑不了"预留心理预期**，并在产品层面提供清晰的兼容性列表与反馈渠道。
